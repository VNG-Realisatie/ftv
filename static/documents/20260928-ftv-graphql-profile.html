Abstract

Abstract

This document defines a profile for authorizing GraphQL requests in the Federatieve Toegangsverlening (FTV) architecture. It specifies (a) a mapping function that turns the GraphQL body of an HTTP request into a list of selected fields, each with its parent type and its arguments, (b) the guarantees the enforcement chain gives about the request the PDP evaluated, and (c) the obligations of the policy engine: every field needs a rule or is denied, and the per-field results combine into one AuthZEN decision. A reference rule model is informative. The profile builds on the NLgov Profile for OpenID AuthZEN and is engine-neutral in its input: any Policy Decision Point (PDP) that accepts an AuthZEN request can implement it.

This document is a profile on the NLgov Profile for OpenID AuthZEN Authorization API. It is a working draft of the FTV workgroup and has no official standing.

1. Introduction

GraphQL [GRAPHQL] lets a data source publish one schema that many consumers query. Each consumer selects the fields it needs. This fits data minimization. It also creates a problem for access control: one HTTP request can ask for any subset of the schema, and that subset is only known at request time.

The NLgov AuthZEN profile [AUTHZEN-NLGOV] defines how a Policy Enforcement Point (PEP) asks a PDP for a decision. It does not say how a GraphQL request maps onto the AuthZEN information model. Without such a mapping, every policy author must parse GraphQL inside the policies. 3. Design Constraints explains why that does not work in practice.

This profile fills the gap with three parts:

  • A mapping function (5. The Mapping Function). It reads the GraphQL body from the AuthZEN request, parses and validates it, and adds a flat list of selected fields to the request. Each field record carries its path, its parent type, and its own arguments. The output is a valid AuthZEN request with extra properties.
  • Enforcement guarantees (10. Enforcement Guarantees). They state that what the PDP evaluated is what the source executes.
  • Policy engine obligations (8. The Policy Model). They state which fields need a rule, which bindings can allow a field, and how the per-field results combine into one decision. A reference rule model (Section 9.6) is informative; a bundle can use another model.

The mapping function is type-aware and policy-blind. It knows the schema. It knows nothing about permissions. All decisions stay in the policies, which the Policy Administration Point (PAP) loads into the PDP. This keeps the design inside the EAM/PxP model of [FTV].

1.1 Scope

A deployment can authorize access to GraphQL data at different places:

Approach Where the PDP is asked Precondition
In front of the endpoint A standard PEP in front of the source asks the PDP for one decision about the whole request, before the source executes it. No change to the implementation of the source. The configuration and the deployment pipeline of the source meet 10. Enforcement Guarantees.
In the resolvers The resolvers of the source, or middleware in its GraphQL server, ask the PDP about objects or fields, at one or more levels of the query. Control over the implementation of the source.
Schema stitching or federation A gateway combines several GraphQL endpoints into one schema. The gateway, each endpoint, or both ask the PDP. Control over the gateway.

This profile specifies the first approach only: generic AuthZEN enforcement in front of a GraphQL endpoint. It does not need control over the implementation of the source, so it also applies when the deployer does not control that implementation. The other approaches are valid. They can give finer control, for example a decision on the data that a resolver loads. They are out of scope for this profile.

The approaches can be combined. A source can also enforce per resolver (2. Model). The source in front of which the PEP sits can itself be a gateway that combines other endpoints. This profile then treats the combined schema as the schema of the source.

2. Model

consumer ──POST /graphql──> PEP
                              │  AuthZEN request:
                              │  subject = caller (from mTLS), action = POST + body,
                              │  resource = request target, context = headers
                              ▼
                            PDP
                              ├─ 1. mapper ([[[#the-mapping-function]]])
                              │     parse + validate body ──> resource.properties.graphql
                              │     {profile, operation, schema, fields[], unverifiable}
                              └─ 2. policy engine ([[[#the-policy-model]]])
                                    bind rules per field, AND ──> ONE decision
                              │
                              ▼
                            PEP: allow → forward unchanged ([[[#enforcement-guarantees]]])
                                 deny  → 401 or 403 ([[[#decision-and-error-transport]]])

One HTTP request gives one AuthZEN evaluation and one decision. The profile does not use the evaluations batch endpoint. Every field record is self-contained so that a later version can fan out to one evaluation per field without changing the record (15.6 Fan-out by the mapper).

The mapper MAY run inside the PDP (as a request pre-processing step before the policy engine) or as HTTP middleware in front of the PDP. Both placements conform. 6.4 Ownership and drift explains why the mapper belongs on the PDP side in practice.

A source MAY additionally enforce per resolver, with its own PDP calls. That is defence in depth and outside this profile.

3. Design Constraints

The following constraints shape the profile. They are stated here so a reader can check every normative rule against them.

  1. GraphQL compliance. The mapper MUST parse any document that is valid under [GRAPHQL]. Where the mapper cannot decide, it MUST deny, not guess.
  2. Policies decide. The schema the source serves MUST NOT carry access rules. The binding between fields and rules is part of the policy bundle and is deployed through the PAP together with the rules.
  3. One decision. One query is allowed or denied as a whole.
  4. Deny by default. GraphQL APIs have no versions. A source can add a field at any time. A data field without a rule MUST be denied.
  5. Independent deployment. The source deploys its API on its own schedule. The PAP deploys the policy bundle on its own schedule. A field the source adds or renames MUST NOT open access: it fails validation until the bundle is updated. A change to a definition that the bundle already contains is not visible in the query. Such a change MUST NOT open access either: guarantee H3 blocks it in the deployment pipelines of the source and of the bundle (6.4 Ownership and drift). Drift MAY close access.
  6. What is judged is what runs. The request the PDP evaluated and the request the source executes MUST be the same request (Section 11).

3.1 Why not solve it in the policies

Only OPA (Rego) has GraphQL builtins (graphql.parse, graphql.parse_query). Cedar, Cerbos, and OpenFGA have none. The Rego AST carries no type information: a field node is {Alias, Name, Arguments, SelectionSet}. To find the parent type of a nested field, a policy must fold the schema down the query path. Rego does not allow recursion, so this becomes one rule per depth level. The result is a large engine module, shipped in every policy bundle, that contains no domain logic and runs on one engine only.

3.2 Why not solve it in the PEP

A GraphQL-aware PEP needs the schema. The schema the policies were written against lives in the policy bundle, which lands at the PDP. A PEP-side mapper needs a second distribution channel for the schema and must keep it in sync with the bundle. This is the coupling constraint 5 forbids. It also replaces an off-the-shelf PEP with a custom one.

3.3 Why not COAZ

COAZ [COAZ] standardizes how a PEP builds an AuthZEN request from a declarative template. It forbids a mapping from fanning out per list element (COAZ Section 2.6). A selection set is a list of N fields, unknown until the request. Only a COAZ GraphQL binding could express this, in the way [COAZ-MCP] binds MCP. No such binding exists as of September 2026. What already matches COAZ: the single evaluation envelope, fail-closed on mapping error, and the trust-anchored subject.id set by the PEP.

4. Requirements on the PEP

4.1 Transport subset

[GRAPHQL-HTTP] allows GET with query parameters, several request media types, and lets servers accept batched or persisted documents. This profile restricts the transport so that the mapper sees exactly what the source executes.

The policy bundle names the GraphQL path (for example /graphql). The PEP MUST send every request it receives for the source, on any path and with any method, to the PDP. The mapper MUST accept only a request that meets all of the following, and MUST fail closed with subcode UNSUPPORTED_TRANSPORT (5.8 Fail-closed conditions) otherwise.

  • resource.id is byte-equal to the GraphQL path in the bundle. No normalisation: /graphql/, /GraphQL, //graphql, and percent-encoded variants do not match. A resource.id with a query string (a bare ? included) does not match.
  • action.name is POST.
  • The Content-Type header in context.headers has media type application/json (compared case-insensitively per [RFC9110]) and no parameter other than charset=utf-8 (parameter name and value compared case-insensitively).
  • No Upgrade and no Content-Encoding header is present.
  • action.properties.body is present and is a string.

The mapper looks up header names case-insensitively. When more than one name matches, or a value is not a string, the mapper fails closed with UNSUPPORTED_TRANSPORT. A PEP MAY omit the body for a media type it does not forward (for example every value other than exactly application/json). The mapper then fails closed.

A deployment MUST configure the source to serve GraphQL on that one path only and to reject the same requests, so that a request the mapper never judged cannot execute (10. Enforcement Guarantees, H1).

4.2 Request content

The PEP MUST send an AuthZEN evaluation request as defined in [AUTHZEN-NLGOV] with the following content.

Slot Content Requirement
subject.type A type that [AUTHZEN-NLGOV] allows. This profile does not fix it. MUST
subject.id The identifier of the calling organisation (for example its OIN), taken from the mTLS client certificate, or from a token that the PEP has checked against that certificate MUST. The PEP MUST set this value itself. It MUST NOT take it from a header or a claim that it has not verified.
action.name The HTTP method as received MUST
action.properties.body The raw HTTP request body as a string that decodes to the same bytes MUST when the body is valid UTF-8 without a byte order mark. Else the PEP omits the body, and the mapper fails closed. The PEP MUST NOT replace invalid bytes.
resource.type "uri" MUST
resource.id The request target (path and query string), byte-for-byte as received (for example /graphql) MUST
context.headers The HTTP request headers as an object with string values. The PEP joins the values of a repeated header with ,. MUST. The mapper reads Content-Type, Upgrade, and Content-Encoding here.
context.traceparent, context.tracestate W3C Trace Context as defined in the Context Properties of [AUTHZEN-NLGOV] SHOULD, as in [AUTHZEN-NLGOV]. When absent, X-Request-ID is the correlation key.
context.time The time the request was received, RFC 3339, as the Context Properties of [AUTHZEN-NLGOV] define SHOULD. When absent, the PDP uses its own clock and records that in the log.

The PEP MUST also send the X-Request-ID header on the API call as [AUTHZEN-NLGOV] describes.

The PEP MUST NOT parse the GraphQL body. The PEP MUST NOT rewrite the request. The PEP forwards the request unchanged on allow (10. Enforcement Guarantees) and returns an error on deny (9. Decision and Error Transport).

The PEP calls the Access Evaluation API endpoint of the PDP as defined by [AUTHZEN-NLGOV]. The PEP MUST treat every outcome other than a well-formed response with "decision": true (timeout, transport error, 5xx, malformed body) as deny. The PEP MUST NOT cache decisions.

5. The Mapping Function

5.1 Input

The mapper first checks the transport (4.1 Transport subset) and the body size limit (5.7 Limits), before it parses anything. It then reads action.properties.body. The body MUST be one JSON object with the members defined by [GRAPHQL-HTTP]:

Member Type Requirement
query string REQUIRED. The GraphQL document.
operationName string or null OPTIONAL. null is treated as absent. An empty string is invalid (GetOperation in [GRAPHQL] compares the string, so "" would be "present" and match nothing). REQUIRED when the document has more than one operation.
variables object or null OPTIONAL. null is treated as absent.
extensions object OPTIONAL. MUST be absent or an empty object unless the bundle lists allowed member names.

The mapper MUST fail closed with subcode INVALID_BODY when:

  • the body is not a JSON object (a JSON array is request batching, not a GraphQL over HTTP request);
  • a member has a type other than listed, or operationName is the empty string;
  • the body has a top-level member other than the four listed (for example documentId or id, which select a persisted document);
  • extensions has a member the bundle does not list; persistedQuery MUST NOT be listed;
  • any JSON object in the body, at any depth, has a duplicate member name. [RFC8259] leaves duplicate names undefined; parsers differ, so the mapper and the source could read different values;
  • a JSON number in the body cannot be represented exactly by the mapper (for example an integer beyond 2^53 in a JavaScript mapper). A value the mapper rounds is not the value the source sees.

The mapper MAY also add resource.properties.declared (7.2 Resource). The mapper MUST NOT remove or change any other property of the AuthZEN request. The raw body stays in action.properties.body. The enriched request MUST remain a valid AuthZEN request.

5.3 Operation selection

The mapper MUST select the operation as follows.

  1. Parse the full document. A parse error fails closed with subcode PARSE_ERROR.
  2. When the document contains no operation definition, fail closed with subcode NO_OPERATION. This check runs before validation, because a fragment-only document also fails validation (Fragments Must Be Used) and the more specific code is the useful one.
  3. Validate the full document (5.4 Validation and the walk.1) before selecting an operation. This catches an anonymous operation next to a named one ([GRAPHQL] Lone Anonymous Operation).
  4. When operationName is present and no operation has that name, fail closed with subcode OPERATION_NOT_FOUND. This follows GetOperation in [GRAPHQL].
  5. When operationName is absent and the document has exactly one operation, select it. When operationName is absent and the document has more than one operation, fail closed with subcode OPERATION_AMBIGUOUS.
  6. When the selected operation is a mutation or subscription, fail closed with code OPERATION_NOT_SUPPORTED. This profile version covers queries only.

5.4 Validation and the walk

The mapper MUST perform validation and the walk as follows.

  1. Validate the whole document against the bundled schema according to the Validation section of [GRAPHQL]. A validation error fails closed with subcode INVALID_QUERY. Because the bundled SDL defines no executable directives (6.1 The schema is part of the policy bundle), the Directives Are Defined rule rejects every executable directive other than the built-in @skip and @include. The set of directives the validator accepts at executable locations MUST be exactly @skip and @include, whatever the validator library knows by default (for example @defer).
  2. The walk starts at the root operation type of the selected operation, with an empty path.
  3. For every field selection with name f on parent type P, the mapper emits a Field with parentType = P, field = f, path = parent path + [response key], alias when present, and on when the selection set that directly contains the field belongs to a fragment with a type condition. When the selection has a sub-selection, leaf = false and the walk continues with the unwrapped return type of P.f as the new parent type (Section 7.2). Otherwise leaf = true.
  4. For an inline fragment ... on T { ... }, the mapper walks the sub-selection with parent type T. The fragment adds no Field and no path segment. Its direct children get on = "T".
  5. For an inline fragment without a type condition, the mapper walks the sub-selection with the current parent type. Its children get no on.
  6. For a fragment spread ...F, the mapper walks the selection set of fragment F with parent type equal to the type condition of F. The spread adds no Field and no path segment. Its direct children get on equal to the type condition of F. A fragment spread more than once produces its fields more than once, once per position.
  7. The mapper emits one Field per selection. It MUST NOT merge selections that share a response key. After validation, two selections with the same response key in the same merged selection set have identical field names and arguments, except when their parent types are different object types ([GRAPHQL] Fields In Set Can Merge). Only that case yields two records with the same path and different args.
  8. Directives @include and @skip: the mapper MUST emit the field regardless of the directive. A field that may be skipped still counts. This is the conservative choice. See 15.3 @skip and @include.
  9. Introspection fields (__typename, __schema, __type): the mapper emits them like any other field. The policy engine drops __typename and the descendants of __schema and __type (8.2 Data fields).
  10. Limits (5.7 Limits) are checked during the walk. The walk MUST stop at the first exceedance.

5.5 Arguments

For every selection, args holds one entry per argument that has a value after the resolution below, keyed by the argument name. Each entry has value and origin. When no entry remains, args is absent.

Variable coercion. Before the walk, the mapper MUST coerce the supplied variables against the variable definitions of the selected operation as CoerceVariableValues in [GRAPHQL] describes: built-in scalars, enums, lists, input objects, and non-null wrappers are coerced; a coercion failure, a null for a non-null variable, or a missing non-null variable without default fails closed with subcode VARIABLE_ERROR. Values of custom scalars (for example BSN) are passed through as the JSON received; the mapper cannot know the source's coercion for them (13. Security Considerations).

Value. value is the argument value as the source executes it: the result of input coercion of the argument literal against the argument's type as CoerceArgumentValues and Input Coercion in [GRAPHQL] define, after variable resolution. This includes: enum values as strings; a single value coerced to a one-item list where the type is a list; input-object fields that are absent and have a declared default filled in with that default; null as null.

Variable resolution. The table applies to the coerced variable values. Rows 3 to 5 concern nullable variables without default; a non-null variable without default that is not supplied already failed coercion.

Case Resolved value
Supplied in variables (including an explicit null) The coerced supplied value.
Not supplied, declared with a default The declared default.
Not supplied, no default, used directly as an argument value The argument is not provided. Argument-definition default applies (below).
Not supplied, no default, used as an input-object field value The input field's declared default when it has one, else the field is omitted from the object.
Not supplied, no default, used as a list item The item is null. (A non-null item type in this position fails validation: All Variable Usages Are Allowed.)

Argument-definition defaults. When an argument is not provided (not written, or resolved to "not provided" above) and the schema declares a default for it, the entry is added with the schema default and origin: "schema-default". This is what the source executes (CoerceArgumentValues in [GRAPHQL]). When an argument is not provided and has no schema default, there is no entry.

Origin. Every entry has origin. Entries whose value references one or more variables also have variables: the list of referenced variable names. Entries whose value contains input-object fields that input coercion filled from a schema default also have schemaDefaults: the list of paths to those fields inside value. Each path is an array, for example ["minimum"], or [0, "minimum"] for an input object inside a list.

origin Meaning
"literal" The value contains no variables.
"variable:<name>" The value is exactly the variable <name>, supplied in variables.
"default:<name>" The value is exactly the variable <name>, resolved to its declared default.
"schema-default" The argument was not provided; the value is the argument's default from the schema.
"mixed" A literal that contains one or more variables (for example [$jaar]); variables lists them.

There is no global argument map. Two selections of the same field with different arguments produce two records with different args.

5.6 Path and field id

path is the list of response keys from the operation root to the field. The response key is the alias when present, else the field name ([GRAPHQL] Response Key). Fragments add no segment. Example: ["a", "naam"] for a: persoon(bsn: "1") { naam }.

The field id is path joined with .. It is a display form for messages and logs. It is not unique: two records can share a path when they sit under different concrete types of one abstract parent (5.4 Validation and the walk.7) or when a fragment is spread twice into one selection set. Where a record must be identified exactly, the profile uses its index in fields[].

5.7 Limits

The mapper MUST enforce the following limits at the stage named. Exceeding any of them MUST fail closed with subcode LIMIT_EXCEEDED. The values are bundle settings; the defaults apply when the bundle does not set a value.

Limit Default Stage and count
Body size in bytes 1 048 576 Before parsing; length of action.properties.body
JSON and GraphQL nesting depth 64 During parsing; nesting of JSON values, and of GraphQL selection sets and value literals
Fragment definitions 100 After parsing; definitions in the document

6. The Schema

6.1 The schema is part of the policy bundle

The policy bundle MUST contain the GraphQL SDL the rules were written against. The SDL MUST NOT define executable directives (Section 6.4.1). The SDL MAY be a subset of the source's schema: types and fields the policies never cover can be left out, except as 6.2 Type resolution requires. A query that selects a field absent from the bundled SDL fails validation and is denied.

The mapper MUST load the SDL from the policy bundle or from a location the bundle points to. The mapper MUST NOT fetch the schema from the source at runtime and MUST NOT use GraphQL introspection. One evaluation MUST use one bundle version for the SDL, the rules, and the bundle settings. When the mapper runs outside the policy engine or loads the SDL from a location outside the bundle, the pinned digest of 6.3 Schema digest is REQUIRED.

6.2 Type resolution

The mapper resolves parent types from the SDL. For a field P.f with a sub-selection, the next parent type is the named type of P.f with list and non-null wrappers removed: [Bedrag!]! gives Bedrag.

For a field selected on an interface without a type condition, the parent type is the interface. On a union, only __typename can be selected without a type condition ([GRAPHQL] Field Selections), so no data field ever has a union as parent type. For a field inside ... on T, the parent type is T.

A binding on an interface field key (Inkomen.jaar) covers that field on every implementing type the source has, whenever the consumer selects the field without a type condition. The bundled SDL MUST contain every implementing type of every interface it contains, and every member of every union it contains. H3 (10. Enforcement Guarantees) requires the source to have exactly those types, so a new implementing type at the source fails the H3 check instead of opening access. A concrete-type key never restricts what an interface key allows: the consumer chooses the parent type by writing or omitting ... on T. A bundle SHOULD NOT combine an unconditional interface key with a conditional concrete-type key for the same field, and a bundle check SHOULD reject it. Rules for sensitive fields SHOULD use concrete-type keys only (13. Security Considerations).

6.3 Schema digest

The mapper MUST compute schema.digest as "sha256:" followed by the lowercase hexadecimal SHA-256 of the UTF-8 bytes of the SDL text it loaded, and MUST put it in the output (5.2 Output). The digest identifies the schema artifact in the bundle. It does not identify the source's schema: the bundled SDL may be a subset and byte-level differences (whitespace, comments, order) change the digest.

The policy bundle MAY pin an expected digest. When it does, the policy engine MUST deny with CONFIG_ERROR / SCHEMA_MISMATCH when schema.digest differs from the pinned value. The digest appears in the decision log, so every decision records the schema artifact it was made against.

6.4 Ownership and drift

The policy author owns the schema in the bundle, together with the rules. When the source adds or renames a field, the new field is absent from the bundled schema. A query that selects it fails validation and is denied. Access reopens only when the policy author updates the schema and the rules in one bundle. Drift is safe, not invisible.

Four kinds of drift are not visible from the query:

  • the source changes the return type of a field that is in the bundled schema: the mapper resolves the old type and rules bind to the old key;
  • the source adds an implementing type to an interface, or a member to a union: interface keys cover it (6.2 Type resolution);
  • the source adds an argument to a field, or an input field to an input object type, that is in the bundled schema: the consumer cannot write it, but the source executes its default;
  • the source adds or changes an argument or input-field default: the mapper resolves the bundled default (5.5 Arguments).

Guarantee H3 (10. Enforcement Guarantees) covers all four. It runs in two places: in the bundle pipeline before a bundle is deployed, and in the source pipeline before a schema change is deployed. The second check closes the time window between a source deployment and the next bundle check. In addition, a rule never allows a checked argument value that comes from a schema default (8.4 Per-field evaluation).

Because the schema travels with the bundle, the mapper belongs where the bundle lands: on the PDP side. A PEP-side mapper would need a second distribution channel for the schema.

8. The Policy Model

The policy engine evaluates the enriched request. 8.1 Rules and binding to 9.5 state what every policy engine MUST do, whatever its rule language and whatever notation the bundle uses for the binding. 8.6 Reference policy model (informative) is informative: it gives a reference rule model that meets these requirements. A bundle MAY use another model.

8.1 Rules and binding

A rule is one unit of policy with conditions. A binding connects a data field to zero or more rules. The binding MUST be part of the policy bundle and MUST be deployed through the PAP together with the rules. It MUST NOT depend on the schema the source serves at runtime.

This profile does not prescribe how the binding is written. Section 9.6 shows rule data that names field keys.

8.2 Data fields

The engine MUST take resource.properties.graphql.fields[] and drop:

  • records whose field is __typename;
  • records whose parentType starts with __ (the children of __schema and __type).

The rest are the data fields. Root fields other than __typename are data fields. The root introspection fields __schema and __type are data fields with keys Query.__schema and Query.__type: introspection executes and returns the source's full schema, so it needs a rule like any other root edge.

When the set of data fields is empty, the decision is deny with code NO_DATA_FIELDS.

When resource.properties.graphql is absent, or its profile is not "ftv-graphql/0.1", the engine MUST deny with CONFIG_ERROR / MAPPER_OUTPUT_MISSING. This covers a mapper deployed as middleware that was bypassed.

8.3 Binding requirements

Whatever the notation, the binding MUST meet these requirements.

  1. Closed world. A data field that no rule binds decides deny, with a client-class per-field code (reference code NO_APPLICABLE_RULE).
  2. Field key. The rules that bind to a record MUST be chosen by its field key parentType.field. The choice MAY also use leaf and whether args is present. It MUST NOT use alias, path, or on: the consumer chooses those.
  3. Arguments. A record with args MUST be allowed only by a rule bound to its field key specifically. A rule bound through the parent type, or through any other group of fields, does not see the arguments.
  4. Root fields. A root field, Query.__schema and Query.__type included, MUST be allowed only by a rule bound to its field key specifically. A rule bound through the root type would cover every entry point, also entry points added to the bundled SDL later.
  5. Each selection. Every record is bound and evaluated on its own, with its own args. Two records with the same field key are two decisions.

8.4 Per-field evaluation

For every data field, the engine evaluates each bound rule against the evaluation context:

Name Value
subject input.subject
field The Field record under evaluation
fields All Field records of the request, including the records 8.2 Data fields drops
resource input.resource without properties.graphql
time context.time

A field decides allow when at least one bound rule evaluates to allow. A field decides deny when no bound rule evaluates to allow. Each deny carries a per-field code (9.2 Reason codes). When several bound rules deny with different codes, a server-class code wins; else the code of the first denying rule in bundle order.

A condition MUST read the arguments it checks from field.args, not from another record in fields. A condition MUST NOT grant access because of the presence or absence of another record: records can share a path (5.6 Path and field id), and a field under @skip is present in fields but may not execute. fields exists for cross-record constraints that only deny (for example: deny when two persoon selections carry different bsn values).

A rule condition that reads an argument the rule needs (for example field.args.jaren) and finds no entry MUST evaluate to deny (reference code CONDITION_FAILED), never to undefined. An undefined result is never an allow.

A rule condition that checks an argument value MUST evaluate to deny (reference code CONDITION_FAILED) when the value comes from a schema default, in whole (origin is schema-default) or in part (schemaDefaults is present). The source executes its own default, which can differ from the bundled one. A consumer that needs the value writes it in the query.

A rule that needs an attribute from a PIP and gets none evaluates to deny with PIP_UNAVAILABLE.

8.5 Aggregation

The engine MUST aggregate as follows.

if graphql output absent or wrong profile: decision = false, code = CONFIG_ERROR, subcode = MAPPER_OUTPUT_MISSING
else if pin set and schema not null and
        digest differs from pin:            decision = false, code = CONFIG_ERROR, subcode = SCHEMA_MISMATCH
else if unverifiable is not null:          decision = false, code = unverifiable.code, subcode = unverifiable.subcode
else if data_fields is empty:               decision = false, code = NO_DATA_FIELDS
else if any field denied with a
        server-class per-field code:        decision = false, code = that code
else if all data fields allow:              decision = true
else:                                       decision = false, code = FIELD_NOT_PERMITTED

The decision context lists every denied field with its per-field code (9.1 AuthZEN response).

Aggregation is AND. A query is allowed only when every data field is allowed. There are no partial results in this profile version. See 15.2 Partial results.

8.6 Reference policy model (informative)

This section is informative. It shows one rule model that meets 8.1 Rules and binding to 9.5. The test vectors of Appendix A use it for their reference decisions.

Rule shape. A rule is data with four parts:

{
  "rule_id": "r-0001",
  "covers_types":  ["Persoon", "Inkomen", "LoonInkomen", "Bedrag"],
  "covers_fields": ["Query.persoon",
                    "Persoon.inkomens",
                    "Inkomen.bedrag",
                    "LoonInkomen.bedrag"],
  "conditions": { "...": "engine-specific" }
}
Part Meaning
rule_id Unique id. Appears in the decision log.
covers_types Set of type names. Leaves of these types can inherit this rule.
covers_fields Set of field keys ParentType.field. These fields bind to this rule.
conditions Predicates over the per-field evaluation context (8.4 Per-field evaluation). Engine-specific.

In this model the rule is the catalog: there is no separate field-to-rule table. Interface fields and concrete-type fields are separate keys. A rule that must cover jaar on the interface and on the concrete type lists both Inkomen.jaar and LoonInkomen.jaar.

Root fields are covered like any other edge or leaf: Query.persoon is a field key. The rule that covers a root field is the natural place for conditions on its arguments, for example that the subject holds consent for the person bsn identifies.

Binding. For every data field with key k = parentType + "." + field:

  1. If any rule has k in covers_fields, those rules bind. Stop.
  2. Else, if the field is a leaf (leaf = true), the record has no args, and parentType is not a root operation type, the rules with parentType in covers_types bind. Stop.
  3. Else no rule binds. The field decides deny with per-field code NO_APPLICABLE_RULE.

Consequences:

  • A leaf inherits from its parent type only when no field-level rule names it. A field-level rule overrides the type-level rule.
  • A leaf with arguments never inherits (8.3 Binding requirements, item 3).
  • A root field binds by field key only (8.3 Binding requirements, item 4).
  • An edge (a field with sub-selection) never inherits. Without a field key it denies with NO_APPLICABLE_RULE. 8.3 Binding requirements does not require this; it is a design choice of the reference model, so that every reachable object type is an explicit decision of the policy author.
  • Two selections of the same field under different aliases bind to the same rules and are evaluated separately, each with its own args.

On deny, the PEP MUST NOT forward the request to the source. It MUST return HTTP 403 or 401; 403 is RECOMMENDED, because the caller is authenticated and the request is refused ([RFC9110]).     {
      "message": "Field not permitted: persoon.inkomens.werkgever",
      "extensions": {
        "code": "FIELD_NOT_PERMITTED",
        "field_id": "persoon.inkomens.werkgever",
        "traceparent": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"

}

Under [GRAPHQL-HTTP] a server that receives a well-formed request returns a GraphQL result; a 403 without a data entry is the shape of a request error result. The PEP is a proxy that never executes the document, so it returns a request error result with the status that [RFC9110] defines for a refused request. The consumer can distinguish "denied" (401 or 403, no data) from "executed with errors" (200, data present).

The PEP MUST NOT copy graphql.admin to the consumer. It SHOULD NOT copy reason_admin; 9.1 AuthZEN response limits its content for a PEP that does.

9.4 Decision log

The PDP MUST log, per evaluation: traceparent when present, else X-Request-ID, subject.id, the enriched request, the decision, the full decision context of Section 10.1, and the bundle version. The log entry is a valid AuthZEN request plus response, so it can be replayed against a policy bundle.

10. Enforcement Guarantees

The mapping function is only sound when the request the PDP evaluated is the request the source executes. The chain MUST give the following guarantees. A deployment that cannot give them does not conform to this profile.

# Guarantee Closes
H1 The request the source receives has the same method, request target, Content-Type, and byte-for-byte body as the request the PDP evaluated (action.name, resource.id, the Content-Type header, action.properties.body). No component between PEP and source normalises, re-serialises, or modifies them. The source is configured to accept only the transport subset of 4.1 Transport subset. A component that changes the request after the decision; a server that reads the query from the URL or accepts GET, batching, or persisted documents.
H2 The source selects the operation to execute by the same operationName the mapper used (5.3 Operation selection). This holds for any conformant GraphQL server. Two operations in one document: PDP judges one, source runs the other.
H3 For every type, field, argument, argument default, input field, input-field default, and return type in the bundled SDL, the source's running schema has the same definition. A field has the same arguments, and an input object type the same input fields, no more and no fewer. Every interface has the same implementing types and every union the same members. H3 compares these elements only. The check MUST run (a) in the bundle pipeline, before a bundle is deployed, against the source's published schema, and (b) in the source pipeline, before a schema change is deployed, against the bundled SDL of the live bundle. A failed check MUST block that deployment. Drift that validation cannot see (6.4 Ownership and drift).

11. Policy Information Points

How the PDP obtains attributes that are not in the request is out of scope for this profile. Examples: consent status from a consent register, pseudonym resolution, subject attributes from a registry. The PDP retrieves them in the way its policy language and the FTV methodology define (for example a PIP call from the policy engine).

Two rules keep the profile independent of that mechanism:

  1. The mapper MUST NOT depend on any attribute obtained from a PIP.
  2. The PDP MUST NOT let anything it obtains from a PIP change resource.properties.graphql.

When a rule needs an attribute from a PIP and the PIP does not answer, the field decides deny with PIP_UNAVAILABLE (8.4 Per-field evaluation, 10.2).

13. Security Considerations

Trust anchor. subject.id set by the PEP from mTLS is the only trusted identity. All other declared attributes (headers, declared, variables) are untrusted input that policies validate.

Fail closed. Every path where the mapper is unsure ends in deny. This includes a missing schema, which turns a configuration error into a denial of service for that endpoint, never into open access.

Transport. A GraphQL server that reads query from the URL, or accepts GET, batching, persisted documents, or WebSocket upgrades, executes requests the mapper never saw. 4.1 Transport subset and H1 close this on both sides: the PEP sends everything to the PDP, the mapper accepts one shape, and the source is configured to accept the same shape.

Duplicate JSON names. With last-wins and first-wins parsers in the field, a body with two query members is two different requests. 5.1 Input rejects it.

Root fields. A root field with no data-field descendant (for example b: persoon(bsn: "x") { __typename }) still executes a resolver with its argument and reveals existence. Root fields are data fields and bind by key (8.3 Binding requirements), so a rule on Query.persoon sees every bsn argument, one record per selection.

Aliases. Two selections of one field under two aliases are two requests for data. A representation that keeps one argument map per name loses one of them. This profile keeps one record per selection with its own arguments (5.4 Validation and the walk.7, 6.5).

Defaults. A variable default or a schema argument default is executed by the source whether or not the consumer sent a value. A mapper that omits them lets a rule of the form "if present, then check" pass a value the rule never saw. This profile resolves both (5.5 Arguments).

Custom scalars. The mapper passes custom-scalar values through as received. A lenient source-side scalar can trim, case-fold, or stringify a value that a deny-list rule did not match. Rules on custom-scalar arguments SHOULD be allow-list rules against exact values, and a deployment SHOULD document the canonical form of each custom scalar.

Multiple operations. Selecting the wrong operation would authorize one operation and execute another. 5.3 Operation selection ties the mapper to the same operationName the source uses (H2).

Schema drift. A field added at the source is denied until the bundle is updated. A changed return type, a new implementing type or union member, a new argument or input field, or a changed default is not detectable from the query. Guarantee H3 blocks these changes in both deployment pipelines. When the source pipeline does not run the H3 check, such a change opens access until the next bundle check; that deployment does not conform to this profile. Rules for sensitive fields SHOULD use concrete-type keys even so.

__typename. Under a permitted edge, __typename reveals the concrete type of each item. A rule that permits Persoon.inkomens accepts that consequence.

Introspection. __schema and __type return the source's full schema, which is a superset of the bundled SDL. They are root data fields (8.2 Data fields) and execute only under a rule that covers Query.__schema or Query.__type. A permitted data field in the same query does not carry them along.

Directives. Ignoring @skip and @include is conservative: a field that might be skipped still needs a rule. Every other executable directive fails validation, because a source-defined directive could change what executes.

Limits. The limits of 5.7 Limits bound the mapper's work and the size of the decision log entry at every stage: body size before parsing, nesting during parsing, validation time, and fan-out during the walk. Fragment fan-out can grow exponentially, so the walk limits are checked at each emission, not after.

Field enumeration. field_id in the consumer-facing error confirms that a field exists in the bundled schema, and the pair INVALID_QUERY versus FIELD_NOT_PERMITTED tells whether a field is in the bundled subset. Validation messages never reach the consumer. A deployment that treats the bundled subset as sensitive MAY omit field_id and MAY report INVALID_QUERY as FIELD_NOT_PERMITTED in graphql.client.

14. Privacy Considerations

The mapper copies argument values, including personal identifiers such as a BSN, into resource.properties.graphql.fields[].args. The decision log of 9.4 Decision log then contains them. How the decision log protects personal data is outside this profile (Open Issue 16.5).

The AND aggregation supports data minimization: a query that asks for one field too many returns nothing. The consumer must shape the query to its permission. No data leaves the source for a denied query.

15. Open Issues

15.1 Field list placement

This draft puts the field list in resource.properties.graphql (the fields are the thing accessed). The alternative is context.graphql (the list is derived by the PDP and never supplied by the caller). The workgroup decides.

15.2 Partial results

All-or-nothing is a feature for data minimization and fits the single-decision hook. A future version could return the permitted fields and list the denied ones in GraphQL errors[]. That needs a response filter after the source, and touches H1.

15.3 @skip and @include

Conservative today. Honoring them moves directive-argument evaluation into the mapper.

15.4 Mutations and subscriptions

Denied today. A mutation asks a different question (which change with which input), and its root fields execute in sequence with side effects. A future version needs its own walk rules and rule model.

15.5 Identifying arguments in the log

Outside this profile. The workgroup decides whether and where to specify it.

15.6 Fan-out by the mapper

In this draft, one AuthZEN evaluation carries the whole field list, and the policy engine loops over it (8. The Policy Model). Engines that cannot loop over a list, such as Cedar and OpenFGA, need engine-specific code in the PDP. That code splits the list into one check per field and combines the results.

A future version can move that split into the mapper. The PEP still sends one evaluation and gets one decision. The mapper then:

  1. makes one evaluation per data field, with the field record in the context;
  2. sends the evaluations to the evaluations endpoint of [AUTHZEN] on the PDP, with the evaluations_semantic option deny_on_first_deny or execute_all;
  3. combines the results as 8.5 Aggregation describes. A missing or malformed result is a deny.

A batch that the PEP builds is not an alternative. The PEP then needs a GraphQL parser and the schema (3.2 Why not solve it in the PEP), and the PEP combines the results. With a fan-out by the mapper, the field list comes from the component that validated the query against the bundled schema. The aggregation stays on the PDP side, and the PEP stays a standard component.

Points to decide:

  • The aggregation of 8.5 Aggregation moves from the policy engine to the mapper. The mapper still knows no rules, but it decides how the per-field results make one decision.
  • One evaluation per field needs its own information model: resource.type, resource.id (the field key), and the context.
  • Rules that only deny over several records (8.4 Per-field evaluation) need the full field list in the context of every evaluation. Otherwise the profile drops these rules.
  • With deny_on_first_deny, the decision log does not list every denied field (9.1 AuthZEN response). execute_all gives the full list, at a higher cost.
  • The mapper must run on the PDP side. A mapper on the PEP side is a custom PEP (3.2 Why not solve it in the PEP).

The record shape of 5.2 Output is self-contained, so a fan-out needs no change to the records.

15.7 Interface duplication

Rules list both the interface key and each concrete-type key when they want both. A future version could let the engine expand interface keys from the schema, with the drift consequence of 6.2 Type resolution made explicit.

15.8 Introspection

Query.__schema and Query.__type need a rule like any root field; a query with only __typename denies with NO_DATA_FIELDS. A bundle-level switch for tooling access could replace the rule.

15.9 Conformance levels

A level without a schema (rules bind on path only, no validation, no types) would let sources without a published schema start. This draft requires the schema.

15.10 Custom scalar canonical forms

The bundle could declare a pattern per custom scalar that the mapper enforces, closing the lenient-coercion gap of 13. Security Considerations.

15.11 Governance

Who maintains the reference mapper and the conformance vectors.

Policy engine The part of the PDP that evaluates rules against the enriched request.
PAP Policy Administration Point. Delivers the policy bundle to the PDP.
PIP Policy Information Point. Delivers extra attributes at decision time.
Source The GraphQL server that executes the query after an allow.
Mapper The component that implements the mapping function of 5. The Mapping Function.
Policy bundle The set of artifacts the PAP loads into the PDP: rules, the schema, and bundle settings. Bundle settings defined by this profile: the GraphQL path (4.1 Transport subset), the pinned schema digest (6.3 Schema digest), the allowed extensions members (5.1 Input), and the limits (5.7 Limits).
Schema The GraphQL SDL the policies were written against. Part of the policy bundle.
Selected field One field selection in the query, after fragment expansion. Two selections of the same schema field under different aliases are two selected fields.
Field record The JSON object the mapper emits for one selected field (5.2 Output).
Response key The alias of a field selection when present, else the field name. This is the key the source uses in the response.
Path The list of response keys from the root of the operation to the selected field.
Parent type The GraphQL object, interface, or union type on which a field is selected.
Field key ParentType.field. The key a rule uses to cover a field.
Field id The path joined with .. Used in messages and logs. Not unique (5.6 Path and field id).
Leaf A selected field without a sub-selection.
Edge A selected field with a sub-selection (an object, interface, union, or a list of these).
Root field A selected field whose parent type is the root operation type of the operation.
Data field A Field record that 8.2 Data fields does not drop. Root fields other than __typename are data fields, Query.__schema and Query.__type included.
Rule One unit of policy, with conditions. A binding connects it to data fields (8.1 Rules and binding).
Coverage The property that every data field has at least one rule.
Fail closed When the mapper cannot produce a complete and correct field list, the decision is deny.

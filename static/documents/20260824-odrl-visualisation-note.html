ODRL Visualisations

The triples an ODRL policy needs, on top of valid ODRL, so a generic viewer can render it.

Introduction

The requirements below make it possible to visualise ODRL policies with generic tooling: one viewer that renders any policy as a readable document, without code per profile or per dataset.

This note assumes valid ODRL 2.2 policies. It lists only the triples a policy needs on top of that, so a viewer can name, group, date, link, and trace what it shows. Every requirement below is used by a working viewer today (the ODRL-AP-NL visualiser). Nothing here is speculative.

Words used: needs = without this triple the feature does not work. should = without this triple the feature works but reads worse.

1. Labels

The viewer never invents names. Names come from the data.

  • Every IRI shown to a person needs one of: rdfs:label, skos:prefLabel, or dct:title.
  • This holds for: actions, targets, parties, left operands, operators, right-operand values, classes, and container documents. ODRL core terms are the exception: the viewer carries their words itself.
  • Labels should carry a language tag (@nl, @en). The viewer picks the label that matches the user's language. In English mode: @en, then no tag, then @nl. In Dutch: the reverse.
  • No label at all → the viewer shows the last segment of the IRI.
  • A blank node with no label and no name-like property shows as "(anonymous)". This is honest but unreadable. Give things labels.

In SPARQL mode the viewer fetches labels one hop from the policy. So labels need to sit in the same endpoint as the policy data.

2. Reusable nodes

  • Rule nodes may be blank nodes, but reuse needs IRIs: a rule shared by an Offer and an Agreement needs to be the same IRI node in both. The viewer then folds it on the agreement card into one row: "from the offer (n duties)". With copied blank nodes the same text repeats on every agreement.

3. Collections of targets

  • A collection lists its members with dct:hasPart.
  • Each member should have an rdf:type from the domain (for example brp:Rubriek), next to odrl:Asset. The viewer groups members under the label of that class.
  • That domain class (the rdf:type value) needs a label per language (for example brp:Rubriek with "Rubriek"@nl, "Data item"@en). The class label becomes the group heading.
  • Members without a domain type all land in one flat group. Nothing breaks.

4. Links between offers and agreements

  • Agreement → Offer: prov:wasDerivedFrom or dct:references, where the object is typed odrl:Offer. This gives the "agreements under this offer" list. The type check matters: the same predicates also point at laws and documents, and those must not show up as offers.

5. Versions and time

The viewer shows one card per policy, with a version navigator. Plain ODRL has no version model, so all of this is extra.

  • A version container is a node that links its versions: container → version with dct:hasPart or pav:hasVersion, or the inverse, version → container with prov:specializationOf.
  • Alternative: a node that lists policies with odrl:hasPolicy (or dcat:hasPolicy) and itself carries dct:valid is treated as a version container.
  • Version data on each version: dct:valid — the period in which it applies; dct:issued — when it was published; prov:wasRevisionOf — the previous version.
  • Status is computed, not stored: current / future / superseded / terminated. Terminated = the container has versions but none applies now.
  • An old version does not need an ODRL type. It counts as a version if it carries one of the date properties above. It should still carry its own rules if you want people to read the old text.

6. What degrades

Nothing above makes the viewer crash when missing. The failure mode is always readability:

MissingResult
label on an IRIIRI tail shown
language tagwrong-language label may show
domain type on membersone flat member group
version datesno version navigator, no status
same-IRI shared rulesduplicated rule text on every agreement
type check on offer linkslaws show up as offers

The rule of thumb behind all sections: everything a person needs to read the policy must be in the triples. If the viewer needs profile code to name or explain something, the data is incomplete — fix the data, not the viewer.

A. ODRL-AP-NL specific

Two profile constructions get special rendering. All other ODRL-AP-NL patterns live in the ODRL-AP-NL specification; they render as normal labelled properties and need no mention here.

A.1 Purpose rules

  • The viewer shows a permission as a purpose rule (its own colour and word) when the action carries a refinement with odrl:leftOperand odrl:purpose. Use that pattern — not a profile-specific property — if you want purpose rendering.
  • The purpose value (the right operand) needs a label.

A.2 Coverage

  • A machine-enforced artifact (a policy bundle, Rego module, …) is typed (for example apnl:PolicyArtifact) and declares prov:wasDerivedFrom <rule-uid> for every rule it covers. The rules it points at need an odrl:uid.
  • The viewer then marks each rule: "technically enforced · ‹artifact›" or "not technically enforced". Uncovered rules stay visible.
